# History acquisition recovery (R01/R02)

The existing operator history scheduler retains its prior-day-only daily candle policy, verified regular calendar, exact mapping, permission checks, shared provider cooldown, pacing, and ten-request maximum per exchange per pass. No current-session candle or adjusted-series qualification is introduced.

V38 adds nullable target_session and claim_token to the existing ledger without resetting attempts. A newer target can supersede an older successful cooldown when the listing is stale; a same-session success, failure cooldown, or unexpired running lease cannot be bypassed. Legacy successful rows may be refreshed once when stale because their target was not recorded. Legacy running leases expire on their existing schedule. New claims expire after 30 minutes and completion is fenced by a unique claim token. This is not a guarantee of exactly-once HTTP after lease expiry. Successful completion requires a positive write count and a complete validated target-date candle in storage; partial writes are retained, but missing targets are failed and retried on the existing failure cooldown.

Established histories (at least 25 observations, latest within acquisition window) get a short incremental request to catch up before later depth/gap repair. Expansion reservations remain 6/4 in quote-screen mode and 8/2 otherwise; unused slots may be borrowed without increasing request budget. Provider entitlement, 429/retry-after, and raw/adjusted protections remain unchanged. The 30-minute lease is an engineering default, not a provider SLA; current HTTP request timeout is 25 seconds, but body/DB processing is not fully deadline-bound. No local restart or live-provider verification is claimed.

Acceptance: run existing Spring unit and database integration tests, then compare actual latest-session counts and attempt statuses after a controlled restart using the existing local acceptance diagnostics. R10 UI and broader provider, calendar and adjusted-data work remain pending. Product certification remains pending.

## R10 — aggregate acquisition diagnostics

The authenticated, read-only GET /api/v1/data-health/history-recovery uses the same verified prior-session calendar and mapped equity universe as the collector. One repeatable-read transaction returns per-venue mapped/current/deep/adjusted counts, recoverable missing and ledger-due missing counts, unexpired/expired claims, last-attempt failures, exclusions, attempt timestamps and shared cooldown. Unknown calendar yields null session-dependent counts, never fabricated zeros. Distinct ISINs across venues are counted separately. The latest successful attempt timestamp is the start of the latest retained successful row, not a completion timestamp or a durable historical success ledger. Depth is a date count, not continuity, adjustment provenance certification or qualification. Due missing excludes adjusted/suspended and unexpired failure/claim cooldowns; it does not include all historical gap/depth work or guarantee an immediate request. No raw keys, tokens or owner data are returned. No new provider requests are made by diagnostics.

Source Readiness now contains a collapsed Automatic historical data recovery panel. Opening it loads data and polls every 120 seconds while visible; closing it cancels polling and in-flight fetches. The displayed net change compares only consecutive successful observations with equal target and mapped listing count, not a rate, cumulative count, or ETA. The query has a 20-second transaction timeout; actual Mac resource performance and recovery counts remain acceptance items. Research eligibility and qualification remain in existing research snapshot diagnostics, not inferred from candle coverage.

## R07 — benchmark and calendar recovery

Price-index history now shares the verified prior-session selector and fenced session-aware ledger with equity recovery. Unknown or special newer dates stop index requests; no fallback to an older date. New missing target sessions can supersede old successful cooldowns while failure, lease and provider cooldown remain authoritative. The index collector requires a provider-validated raw price-index candle at the exact stored regular close (not a manual row) before success. Calendar checks exclude holidays, weekends, contradictory special sessions and malformed IST open/close bounds. Index candle revisions increment only on changed OHLCV; repeated identical observations preserve revision. One provider request per pass and broad-index priority remain unchanged. Calendar backfill prioritizes recent dates and older weekdays while still requesting older weekends after those gaps; existing contradictory records are never overwritten. Calendar attempt completion uses the stored session policy, not merely the count of venue rows. This is not independent official calendar certification. Official TRI remains distinct from a price index.

The authorized TRI importer now retains its last-good per-index evidence in a separate additive local archive, never promotes failed downloads into current qualification, and reports aggregate archive/failure counts. A shared persisted publisher cooldown applies across configured index URLs after HTTP 429/503, respecting valid Retry-After values and a six-hour floor. No new endpoint was invented. Publisher historical reports at https://www.niftyindices.com/reports identify total and net total-return values, and https://www.niftyindices.com/offerings/data-subscription describes data subscriptions; a documented authorized direct automated CSV endpoint for the required indices has not been established. Existing local exports and authorized CSV manifest remain the only enabled routes. Actual benchmark key access, 470-day calendar coverage, current gross TRI and historical scheme benchmark mandate remain external/runtime acceptance items.
